Store 可观测 Trace：三层 Diff/DiffElement 树 · get/set 键序列 · 命中率

同一棵 site(level-0) → device(level-1) → interface(level-2) 树，dump 后分别走 LocalStore 与内存假 Redis (FakeRedis)。

覆盖：热重建、root 为空、父子同时未命中的并发回源、索引失效回源修复、pickle/JSON 双协议交叉读。

三处取舍（互相咬住，注释与本页同源）

1. pickle 与 JSON 双协议共存：先试谁，读到对方的键怎么降级

读取时先尝试 pickle（能无损还原 Diff/DiffElement 对象图）；若 blob 不是 pickle (UnpicklingError) 或不是合法 UTF-8/JSON，则降级用 json.loads 再解一次。被降级解出的键标记为 cross-protocol，只读不重写：键的字节归写下它的那个协议所有，本端不会把它偷偷改写成自己的协议。页面上这类命中单独计数，仍计入命中率。

2. root 键命名 vs 父子键前缀扫描：临时遍历还是维护索引，失效后谁付代价

键布局把 idx(集合) 和 root:<tree>(顺序) 放在 node: 前缀之外，子节点扫描 node:* 在命名上就不可能扫到 root/index，后端还会再过滤一层 :node:。常规重建 O(1) 读 root 拿前序、用 idx 集合校验；一旦 root/idx 丢失或与节点不一致，代价由读者承担：一次性 node:* 全量扫描并回建索引与 root，下一次读又回到 O(1)；写入方从不会为索引修复阻塞。root 键缺失且一个节点都没有时，判定为真空树 root-empty。

3. 签名统一后，父子键同时未命中的并发回源：谁去重、重复写要不要覆盖

BaseStore 统一 get_or_load_raw(key, loader) 签名，但去重落在各自真正掌控的层：LocalStore 同进程，持有 in-flight 注册表 + 锁，同键并发只回源一次，后到者共享结果；RedisStore 看不到别的进程，把保证下沉到服务端 SET NX——可能重复算，但只有首个写入生效，竞态失败者改为读出胜者的值。两家可观测契约一致：first writer wins，重复写入不覆盖(write-skipped)，迟到的父节点不可能盖掉先落地的更新子树。
